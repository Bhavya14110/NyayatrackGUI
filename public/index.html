Reschedule a hearing

Only a hearing that has not been held yet (outcome Listed) can be moved. The database refuses a courtroom or judge that is already booked at that time (FR-28), updates the cause list, and queues a notification for every party and advocate (FR-05a, FR-12).

New date and time

Transfer a case

Hand a Registered or Hearing case over to another judge (FR-09). The stored procedure sp_transfer_case closes the current assignment, opens the new one with your handover note (FR-22) and moves the coming hearings to the new judge.

Audit trail

Every change to a case, newest first, from the append-only audit log (view v_case_timeline): who made it, when, and only the fields that changed (FR-23, FR-24, FR-25).

Litigant view

This is exactly what the litigant portal shows a party (FR-07, FR-29, NFR-04). The request runs as the database role nyaya_litigant with nyaya.personid set to the party, so the database itself limits it to that person's own cases (NFR-02).

Advocate view

This is the advocate's multi-case dashboard (FR-30). The request runs as the database role nyaya_advocate with nyaya.personid set to the advocate, so the database itself limits it to the cases in which this advocate represents a party (NFR-02).

Notification feed

Every hearing moved in the last 24 hours, one row per party and advocate to tell (FR-05a). The feed is read through the database role nyaya_notifier, which can read nothing else. Phone numbers are masked (NFR-02).

Sending (FR-05b) needs an SMS / e-mail gateway, which this project does not have, so “Send” hands the message to a simulated sender and logs it in the server console.
